Architecture

Overview

preview-runner runs as one server pod and many worker pods. The server pod is the only entry point: appx calls its API, and users' browsers load previews through its proxy. Worker pods run the app previews and browser sessions. Each app is pinned to one worker pod, so its dev server and its browser sessions share that pod's localhost, and the dev server's port never leaves the pod.

Placement is decided per call from Redis. A worker pod writes a key for each sandbox and browser session it holds, and the server sends a workspace's calls to the worker pod its key names. A workspace with nothing running goes to the live worker pod with the most free sandbox slots. See Placement controller.

Proxy

The proxy runs on the server pod, on its own port, PROXY_PORT: a plain HTTP server, apart from the API's Fastify, with none of its hooks. The Ingress sends PREVIEW_DOMAIN and its subdomains to PROXY_PORT, and the API's domain to PORT. For each request, HTTP or WebSocket, the proxy finds its workspace, asks the placement controller for the workspace's worker with any, and sends the request to that worker's port forwarder over mTLS, presenting server.crt, with x-workspace-app set to the workspaceId. The proxy always sets that header itself, so a browser can't name a workspace. The app is served at the root of its host, so its absolute links such as /css/… keep working.

Workers

A worker pod is the runner started with APP_MODE=worker. It runs the sandboxes and browser sessions of the workspaces placed on it and reports on itself to Redis: its load through the stats reporter, its logs through a log stream. Both are keyed by its pod name, which a StatefulSet keeps across restarts, so the server pod reads every worker's state from Redis and never has to find or call a worker to learn about it.

Authentication

A worker registers with the server on every boot. The request and the reply are sealed with a key derived from WORKER_JOIN_SECRET, which the server and every worker read from one Kubernetes Secret; the secret itself is never sent. At registration the server signs the worker's certificate with WORKER_CA_KEY, and on its own boot it signs its client certificate, server.crt, with the same key. Calls from the server to a worker's internal API, and preview traffic from the proxy to its port forwarder, are mTLS: each side presents its certificate and checks the other's against WORKER_CA_CERT.

A worker makes a new key and gets a new certificate on every boot, and registers again before the certificate expires. The server calls a worker only while its pods:<hostname> key holds stats, so a stopped worker drops out within 30 s. The Postgres row records the worker for the machines page; routing never reads it.

PartSetting
SealingAES-256-GCM with a key derived from WORKER_JOIN_SECRET by HKDF-SHA256, a random 12-byte nonce per message. A request that fails to open, or whose time is more than 60 s off, gets 401. The reply carries the request's nonce, so it can't be replayed to another registration.
Requesthostname (the pod name), csr (PEM, subject and SAN the hostname), address, time.
Replycert, the worker's certificate signed with WORKER_CA_KEY, valid for one year; caCert, WORKER_CA_CERT, which the worker checks client certificates against; statsKey, pods:<hostname>, a pattern fixed by the server; additional data, TBD.
CAWORKER_CA_KEY and WORKER_CA_CERT, in the Kubernetes Secret, mounted into the server only. The server signs each CSR whose hostname matches the request's, and on every boot signs server.crt for itself: CN server, client auth only, kept in memory. A worker registers again 7 days before its certificate expires and swaps the new one into its listener without restarting.
RedisThe server writes hostname and address to pods:<hostname> with a 30 s expiry. Once the worker serves HTTPS, its stats reporter runs every 10 s: EXPIRE pods:<hostname> 30, then HSET its stats. An EXPIRE that finds no key means the key was lost, and the worker registers again. Placement and calls use only a key that holds stats, so a worker is called only once it serves HTTPS.

The server presents server.crt and checks the worker's certificate against WORKER_CA_CERT with the hostname as the server name; one connection pool serves every worker. The worker requires a client certificate signed by the CA, or the handshake fails, and answers 403 to one whose CN isn't server.

Stats reporter

Once a worker serves HTTPS, it writes the hash below to the key the server gave it at registration, pods:<name>, every 10 s with HSET, then EXPIRE 30. It writes its hostname and address each time, so a key lost in Redis is whole again after the next report. A worker whose key has expired is gone as far as placement is concerned. The machines page lists every worker in the workers table and shows it live when reportedAt is under 30 s old, stale otherwise.

Placement controller

A module both pods run, services/placement. A worker writes a key to Redis for each sandbox and browser session it holds, and the server reads those keys to pick the worker for each call. A workspace's sandbox, execs, app traffic and browser sessions stay on one worker, so they share its localhost.

KeyValueLifetime
placement:workspace:<workspaceId><name>:<bootId> of the worker running its sandboxSANDBOX_IDLE_MS, 15 min, from the claim or the last lookup; the proxy looks it up every minute while a WebSocket to the workspace is open
placement:session:<sessionId><name>:<bootId> of the worker holding its tabBROWSER_IDLE_MS, 5 min, from the claim or the last lookup
Worker sideWhenWhat it does
Claim a workspaceThe sandbox manager starts a sandbox, on launch or on a wakeSET NX with the TTL. A key holding this worker's <name>:<bootId> counts as claimed; one holding another's fails the request with 409 before a port is taken.
Release a workspacestop, or the sandbox exits: the idle sweep, shutdown, or exiting on its ownDeletes the key if it holds this worker's value. An exit releases only if its sandbox is still the workspace's current one.
Claim a sessionThe chromium manager opens the session's tab, on create or on a reopenSET with the TTL.
Release a sessionThe tab closes: close, the idle sweep or shutdownDeletes the key if it holds this worker's value.

On the server, a call names what it needs from the workspace, and the controller returns the worker to call. Each lookup is a GETEX that renews the key's TTL, so a key in use lives as long as its sandbox or tab and a key nobody looks up expires with the idle sweep. A key whose worker is not live is deleted and treated as no key.

Logging

Each worker writes its logs to two places: stdout, for the container runtime, and a Redis stream named after the pod, logs:<name>, for the server's machines page. The server reads any worker's logs from Redis without calling the worker, and the logs of a worker that has died can still be read.

The stream is for debugging, not for keeping records. It holds a worker's most recent lines and is gone a day after the worker stops writing. Anything a user needs later, such as why a launch failed, belongs on its Postgres row, as sandbox_activities already does.

PartSetting
What goes inEvery line the worker's logger writes at LOG_LEVEL and above, as one entry with one field, line: the same JSON line written to stdout. Every line carries component, the module that wrote it, such as port-forwarder or sandbox-manager. Chromium's stdout and stderr go through the logger as component: "chromium". A sandbox's own output stays in its log files; see Sandboxes. The server pod logs to stdout only.
WriteThe transport flushes every second or every 200 lines in one pipeline: XADD logs:<name> MAXLEN ~ LOG_MAX_LINES * line …, then EXPIRE logs:<name> LOG_TTL_HOURS. If Redis is slow or down it keeps the newest 1,000 lines, and the next flush that succeeds adds one line with the number dropped. Logging never blocks or fails the worker.
LimitsLOG_MAX_LINES, 10,000 by default, so a noisy worker can't fill the Redis memory that stats, placements and logins share. LOG_TTL_HOURS, 24 by default: a restarted worker keeps its name and appends to its stream, and a removed one's stream stays readable until it expires.
ReadNewest: XREVRANGE logs:<name> + - COUNT 100. Older, on scroll: the same from (<oldest id shown>; fewer than 100 back is the start of what is kept, marked on the page. Live: XREAD BLOCK 15000 from the newest id shown, pushed over server-sent events.

Sandboxes

Each worker pod runs the sandboxes of the workspaces placed on it, one per workspace. The sandbox plugin, plugins/sandbox.ts, owns them in memory. The workspaces row records each workspace's status, and only the worker running its sandbox writes it.

The internal API and the port forwarder share one port, 4002. A request carrying x-workspace-app: <workspaceId> is app traffic, whatever its path: the forwarder takes it over before routing and sends it to the workspace, so an app's own /internal/… routes reach the app. Any other request is an internal API call. A WebSocket upgrade with the header is forwarded the same way; one without it is refused.

Lifecycle

EventWhat happens
Any status changeThe row's status is running while the background process runs, stopped otherwise.
LaunchAlready starting or running → 409. No free pool port → 503. Otherwise its env is PORT = port, then the workspace's env, then env, each winning over the one before. Take the port, start it, save it with that env to the row's launch_options and return at once. In the background: run command with its port mapped to 127.0.0.1:<pool port> → running once it listens. No listener within 90 s → failed.
Request, runningThe port forwarder sends it to 127.0.0.1:<port>. Requests, open WebSockets and running execs joined to it count as use.
Request, stoppedThe port forwarder wakes it through the manager: the row has launch_options → start it again exactly as launched and hold the request until running, up to 90 s. Still starting after that → 503 with Retry-After. No launch_options → 503.
Request, failed502. Traffic doesn't relaunch it; launch does.
Execsh -c in the workspace's confinement, with the workspace's env and env on top. While the background process runs, it joins that process's network namespace: localhost:<port> reaches it, it gets PORT = that port, and the launch's network applies. With nothing running, its own namespace with open egress and no PORT. Its stdout and stderr go together to its own log, and output is the last 16 KB of it; the log is deleted once read. At timeoutMs (2 min default, 4 min max) the process tree is killed, timedOut is true and exitCode is null.
ActivityEvery launch, a relaunch woken by a request included, and every exec adds a sandbox_activities row as running before it starts. An exec settles when it ends: succeeded on exit code 0, else failed, with its output. A launch settles at ready: succeeded once it answers on its port, failed if it exits or times out first, with the last 16 KB of its log so far; one with no free pool port is failed at once. Later crashes show in its logs, not here. The workspace page's Sandbox activity tab lists them, newest first, 20 to a page. Kept until the workspace is deleted.
StopClear the row's launch_options first, so requests no longer wake it → kill the process tree → free the port → stopped. Nothing running → already stopped.
LogsThe last tail lines of stdout and stderr together, in the order written, with blank lines and terminal colour codes left out. Each process writes to its own file in the pod's temp folder. After a stop or a crash they stay until the next launch. The idle sweep and a pod shutdown delete them, and so does a pod restart.
Background process exits on its ownFree the port → failed.
Idle, 15 min with no traffic, open WebSocket or running execThe sweeper stops it, deletes its logs and keeps the row's launch_options. The next request wakes it. Logs calls don't count as use.
A worker pod diesPlacement moves the workspace. The next request wakes it on the new worker from the row's launch_options.
A worker pod shuts downStop every process and delete its logs → their rows stopped. Their launch_options stay, so the next request wakes them.

Confinement

LayerSetting
NamespacesIts own user, pid, ipc, uts, cgroup and network namespaces.
Files/workspace is WORKSPACES_DIR/<workspaceId> on the shared volume, read-write. Deps folders come from the deps cache at SANDBOX_DEPS_ROOT/<workspaceId>, picked by the manifests the workspace has, at its root and up to 3 folders down: package.json → node_modules, composer.json → vendor, pyproject.toml or requirements.txt → .venv, Gemfile → vendor/bundle with BUNDLE_PATH set under the workspace's env. NetworkOne namespace per workspace through pasta, made by launch; an exec joins it while the background process runs, else gets its own. Inbound: only the launch's port, mapped to the pod's 127.0.0.1:<port>. Outbound: only loopback leaves the namespace. The internet is reached through the network controller, an HTTP proxy at 127.0.0.1:3128 inside every namespace, mapped by pasta to the controller's own port on the pod. It applies the launch's allow and deny lists to each host name and refuses private addresses; an exec's own namespace reaches every public host. Tools that ignore the proxy settings can't reach the internet. Nothing on the pod or cluster: not other sandboxes, not Chromium, not the internal API on 4002.
LimitsOne cgroup per workspace, shared by its launch and every exec, caps memory, CPU and process count, so one workspace can't starve the pod.
EnvironmentPORT = the launch's port, the workspace's env over it, the command's env on top, plus PATH, LANG, LC_ALL, TZ. Under them, the proxy settings that point at the network controller: HTTP_PROXY, HTTPS_PROXY and their lowercase forms, NO_PROXY for localhost, and NODE_USE_ENV_PROXY. Nothing else from the runner.
Local devSANDBOX_MODE=none runs unconfined, allowed only with NODE_ENV=development.

Lifecycle

EventWhat happens
A worker pod startsIts chromium plugin, plugins/chromium.ts, starts the session manager, which starts its one Chromium in its own confinement and connects to it over CDP. Then the plugin starts the sweeper.
CreateInsert the row with status alive → open a context with the network rule and one tab, filmed if record. While Chromium is restarting, 503.
CallLoad the row → 404 if its status is closed → run the call's ops code in a runner, one call at a time per session → write url, storageState, lastUsedAt.
Call, tab goneClose the session as below, without a video if the tab died with Chromium → 404.
runStart a runner with the LLM's code and the tab's id → it connects to Chromium over CDP, finds the tab, runs async (page) => … and prints the result → write url, storageState, lastUsedAt. It holds the session's turn, so no other call runs on the tab meanwhile.
A call times outKill the runner. The tab stays. The run answers with the timeout in its error; any other op answers 504.
CloseClose the context → save the video into the workspace at browser/<id>.webm if recorded → set status to closed. The row is kept.
Idle, 5 min without a callThe plugin's sweeper closes the session as above.
Chromium exitsThe session manager starts a new one and reconnects. Tabs in memory are dropped; each session's next call finds its tab gone. Until Chromium is back, creates get 503.
A worker pod restarts or diesIts Chromium and tabs are gone → each session's next call finds its tab gone.
A worker pod shuts downIts plugin stops the sweeper and closes every session as above, then stops Chromium.

LayerChromiumRunner

FilesSystem paths and the browser build read-only. /tmp empty, holding the profile. No workspace, no service account token.System paths, Node and the runner's playwright read-only. /tmp empty.
NetworkIts own namespace through pasta. Inbound: only CDP, from the pod's 127.0.0.1:<BROWSER_CDP_PORT>. Outbound: DNS, public addresses, and the pool ports 4100–4149 on the pod's loopback.
