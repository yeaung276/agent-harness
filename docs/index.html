Architecture

Overview

preview-runner runs as one server pod and many worker pods. The server pod is the only entry point: appx calls its API, and users' browsers load previews through its proxy. Worker pods run the app previews and browser sessions. Each app is pinned to one worker pod, so its dev server and its browser sessions share that pod's localhost, and the dev server's port never leaves the pod.

Placement is decided per call from Redis. Worker pods publish their load, and the first call for an app claims the worker pod with the most headroom. The claim holds until that pod stops reporting.

Components

ComponentPodWhat it does
Preview proxyServerTakes every request that carries the signed preview cookie, HTTP and WebSocket, and sends it to the cookie's app on its worker pod. /__preview/view sets the cookie in exchange for a view token another service mints; the proxy verifies the cookie and reads the appId. The app is served at the root of the preview host, so its absolute links such as /css/… keep working.
preview + browser APIServerThe endpoints appx calls. Finds the app's worker, for a session through its row's appId, and forwards each call to that worker's internal API. The worker writes the rows.
Placement controllerServerA module both of the above use: appId → worker pod, through Redis.
Internal APIWorker/internal/sandbox/* and /internal/chromium/*. Drives this pod's sandbox and Chromium.
Port forwarderWorkerOn the pod's own port, 4002. Hands <appId> traffic to localhost:<port>.
SandboxWorkerRuns each app's dev server on a port from PREVIEW_PORT_MIN–MAX, bound to 127.0.0.1.
ChromiumWorkerThe chromium plugin, plugins/chromium.ts: one Chromium in its own network namespace, one page per session. See Browsers.
Stats reporterWorkerWrites this pod's load and address to Redis every 10 s.

Redis keys

KeyValueWritten byLifetime
pods:<name>cpu, memory, previews, sessions, addressA worker's stats reporterExpires 30 s after its last write.
placement:<appId>Worker pod namePlacement controller, SET NXUntil that worker's pods key is gone; then the next call replaces it.

Scaling and failure

WhenWhat happens
A worker pod is addedIt starts reporting and takes new apps by headroom. Apps already placed stay where they are.
A worker pod diesIts pods key expires within 30 s. The next call for each of its apps places the app on another worker; the preview restarts there. Its browser sessions are gone; each one's next call closes it and answers 404.
The server pod restartsRows are in Postgres and placements in Redis, so nothing is lost. Previews and pages on the workers keep running.
Two calls place one app at onceSET NX lets one win; the other reads the winner.
NetworkA NetworkPolicy lets only the server pod reach the workers' port 4002. Sandbox ports bind to 127.0.0.1 and never leave the pod.

API

What appx and users' browsers call on the server pod. /__preview/view is checked first, with or without a cookie. Then a request that carries the signed preview cookie is app traffic, whatever its path, so an app's own /v1/… routes reach the app. Any other request is an API call: it finds the app's worker through the placement controller, a session through its row's appId, and forwards to the worker's /internal route. 503 means no worker has room or the app's worker can't be reached.

A request without the cookie reaches the API, so the API's mTLS check must be on before the preview host is public. /__preview/view is the one public route; its token is its authentication.

GET/__preview/viewExchange a view token for the preview cookie, then open the app at /

Query

{
  "type": "object",
  "required": [
    "appId",
    "token"
  ],
  "properties": {
    "appId": {
      "minLength": 1,
      "maxLength": 64,
      "type": "string"
    },
    "token": {
      "minLength": 1,
      "type": "string"
    }
  }
}

The token is an HS256 JWT { appId, exp } another service mints with PREVIEW_TOKEN_SECRET. It must verify, be unexpired and name the same appId.

Response 302

Location: / and Set-Cookie: promptx_preview=<JWT { appId, exp }>; HttpOnly; Secure; SameSite=None; Partitioned; Path=/. The cookie is signed with the same secret and lasts 12 h.

Sandboxes

Each worker pod runs the sandboxes of the workspaces placed on it, one per workspace. The sandbox plugin, plugins/sandbox.ts, owns them in memory. The workspaces row records each workspace's status, and only the worker running its sandbox writes it.

The internal API and the port forwarder share one port, 4002. A request carrying x-workspace-app: <workspaceId> is app traffic, whatever its path: the forwarder takes it over before routing and sends it to the workspace, so an app's own /internal/… routes reach the app. Any other request is an internal API call. A WebSocket upgrade with the header is forwarded the same way; one without it is refused.

EventWhat happens
Any status changeThe row's status is running while the background process runs, stopped otherwise.
LaunchAlready starting or running → 409. No free pool port → 503. Otherwise its env is PORT = port, then the workspace's env, then env, each winning over the one before. Take the port, start it, save it with that env to the row's launch_options and return at once. In the background: run command with its port mapped to 127.0.0.1:<pool port> → running once it listens. No listener within 90 s → failed.
Request, runningThe port forwarder sends it to 127.0.0.1:<port>. Requests, open WebSockets and running execs joined to it count as use.
Request, stoppedThe port forwarder wakes it through the manager: the row has launch_options → start it again exactly as launched and hold the request until running, up to 90 s. Still starting after that → 503 with Retry-After. No launch_options → 503.
Request, failed502. Traffic doesn't relaunch it; launch does.
Execsh -c in the workspace's confinement, with the workspace's env and env on top. While the background process runs, it joins that process's network namespace: localhost:<port> reaches it, it gets PORT = that port, and the launch's network applies. With nothing running, its own namespace with open egress and no PORT. Its stdout and stderr go together to its own log, and output is the last 16 KB of it; the log is deleted once read. At timeoutMs (2 min default, 4 min max) the process tree is killed, timedOut is true and exitCode is null.
ActivityEvery launch, a relaunch woken by a request included, and every exec adds a sandbox_activities row as running before it starts. An exec settles when it ends: succeeded on exit code 0, else failed, with its output. A launch settles at ready: succeeded once it answers on its port, failed if it exits or times out first, with the last 16 KB of its log so far; one with no free pool port is failed at once. Later crashes show in its logs, not here. The workspace page's Sandbox activity tab lists them, newest first, 20 to a page. Kept until the workspace is deleted.
StopClear the row's launch_options first, so requests no longer wake it → kill the process tree → free the port → stopped. Nothing running → already stopped.
LogsThe last tail lines of stdout and stderr together, in the order written, with blank lines and terminal colour codes left out. Each process writes to its own file in the pod's temp folder. After a stop or a crash they stay until the next launch. The idle sweep and a pod shutdown delete them, and so does a pod restart.
Background process exits on its ownFree the port → failed.
Idle, 15 min with no traffic, open WebSocket or running execThe sweeper stops it, deletes its logs and keeps the row's launch_options. The next request wakes it. Logs calls don't count as use.
A worker pod diesPlacement moves the workspace. The next request wakes it on the new worker from the row's launch_options.
A worker pod shuts downStop every process and delete its logs → their rows stopped. Their launch_options stay, so the next request wakes them.

Confinement

LayerSetting
NamespacesIts own user, pid, ipc, uts, cgroup and network namespaces.
Files/workspace is WORKSPACES_DIR/<workspaceId> on the shared volume, read-write. Deps folders come from the deps cache at SANDBOX_DEPS_ROOT/<workspaceId>, picked by the manifests the workspace has, at its root and up to 3 folders down: package.json → node_modules, composer.json → vendor, pyproject.toml or requirements.txt → .venv, Gemfile → vendor/bundle with BUNDLE_PATH set under the workspace's env. A launch and every exec get the same ones, so an install in an exec is what the launch uses. Deleting the workspace deletes its deps. System paths read-only. /tmp empty; HOME=/tmp.
NetworkOne namespace per workspace through pasta, made by launch; an exec joins it while the background process runs, else gets its own. Inbound: only the launch's port, mapped to the pod's 127.0.0.1:<port>. Outbound: only loopback leaves the namespace. The internet is reached through the network controller, an HTTP proxy at 127.0.0.1:3128 inside every namespace, mapped by pasta to the controller's own port on the pod. It applies the launch's allow and deny lists to each host name and refuses private addresses; an exec's own namespace reaches every public host. Tools that ignore the proxy settings can't reach the internet. Nothing on the pod or cluster: not other sandboxes, not Chromium, not the internal API on 4002.
LimitsOne cgroup per workspace, shared by its launch and every exec, caps memory, CPU and process count, so one workspace can't starve the pod.
EnvironmentPORT = the launch's port, the workspace's env over it, the command's env on top, plus PATH, LANG, LC_ALL, TZ. Under them, the proxy settings that point at the network controller: HTTP_PROXY, HTTPS_PROXY and their lowercase forms, NO_PROXY for localhost, and NODE_USE_ENV_PROXY. Nothing else from the runner.
Local devSANDBOX_MODE=none runs unconfined, allowed only with NODE_ENV=development.

Lifecycle

EventWhat happens
A worker pod startsIts chromium plugin, plugins/chromium.ts, starts the session manager, which starts its one Chromium in its own confinement and connects to it over CDP. Then the plugin starts the sweeper.
CreateInsert the row with status alive → open a context with the network rule and one tab, filmed if record. While Chromium is restarting, 503.
CallLoad the row → 404 if its status is closed → run the call's ops code in a runner, one call at a time per session → write url, storageState, lastUsedAt.
Call, tab goneClose the session as below, without a video if the tab died with Chromium → 404.
runStart a runner with the LLM's code and the tab's id → it connects to Chromium over CDP, finds the tab, runs async (page) => … and prints the result → write url, storageState, lastUsedAt. It holds the session's turn, so no other call runs on the tab meanwhile.
A call times outKill the runner. The tab stays. The run answers with the timeout in its error; any other op answers 504.
CloseClose the context → save the video into the workspace at browser/<id>.webm if recorded → set status to closed. The row is kept.
Idle, 5 min without a callThe plugin's sweeper closes the session as above.
Chromium exitsThe session manager starts a new one and reconnects. Tabs in memory are dropped; each session's next call finds its tab gone. Until Chromium is back, creates get 503.
A worker pod restarts or diesIts Chromium and tabs are gone → each session's next call finds its tab gone.
A worker pod shuts downIts plugin stops the sweeper and closes every session as above, then stops Chromium.
